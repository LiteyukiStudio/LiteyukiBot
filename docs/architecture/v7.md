# LiteyukiBot v7 Architecture

## Boundaries

The `liteyukibot-v7-kernel` distribution owns protocol-neutral services,
event ordering, action types, shared lifecycle contracts, bridge contracts,
and the portable Runtime API. The branded `liteyukibot-v7` distribution owns
the CLI and currently composes a single-host application. Root composition
still hosts native plugin lifecycle, the
standalone Broker service, plugin management, and local observability while
Alpha14 extracts those implementations. Installed native
plugins are trusted code; process separation is a lifecycle and dependency
boundary, not a hostile-code sandbox.

The kernel dependency budget is intentionally small: Pydantic and Yukilog.
YAML and HTTP remain root-composition concerns. Framework hosts and adapters are separately
published bridge packages discovered through `liteyukibot.bridges` entry
points, so the kernel never depends on or imports a framework. uv exclusively
owns project resolution and locking; runtime package installation is not part
of the core.
The kernel distribution provides the independent `liteyukibot_kernel`
namespace. The root `liteyukibot` namespace retains deliberate compatibility
re-exports so existing component imports resolve to the same kernel objects;
its facade loads composition-owned APIs lazily. The kernel wheel never imports
root composition, a framework, WebUI, Broker service, daemon, or plugin
installation implementation.

The first formal v7 product boundary is CLI-first. WebUI is retained as the
optional `liteyukibot-v7-webui[server]` distribution with dedicated CI and
publishing; it is not a root extra or a member of the signed CLI release
bundle. Root may preserve optional `web` control commands, but normal CLI
startup and qualification do not install or load the WebUI package.

## Lifecycle

`LiteyukiApp` creates an immutable settings snapshot, event bus, service
registry, plugin manager, local control server, and optional HTTP server. The
standalone B7 broker is independently host-initialized; it is not an app
bootstrap or child supervisor. When a reserved `broker.bridges.<id>` entry has
`kind = "kernel"`, the app registers one in-process full broker peer after
native plugins start and stops it before EventBus teardown. This does not start
the broker or make it a child supervisor. Legacy runtime-supervisor code
remains only as historical compatibility context and is not selected by the v6
configuration schema. Failures trigger reverse cleanup and shutdown rejects new
work before owned tasks are stopped.

Native plugins are explicitly enabled and resolve from the
`liteyukibot.plugins` entry-point group or explicitly named local modules. An
entry point returns `PluginDefinition(manifest, setup)`. `setup(context)` is
async and may return start/stop callbacks. Service contracts use `name@major`
keys, one provider per key, and a startup dependency graph.

The kernel registers `liteyukibot.kernel.status@1` before plugin topology
resolution. Its provider exposes only frozen operational snapshots: version,
application state, monotonic uptime, plugin/runtime states, and EventBus
backlog. Native plugins do not receive a general `LiteyukiApp` handle.

### Native and Cordis Extension API v2 hosts

Cordis is an optional Python in-process composition package. It is independent
from the Native host and has equal event-semantic authority, but does not claim
Koishi compatibility. Native
and Cordis are separate hosts, discovered through `liteyukibot.plugins` and
`liteyukibot.cordis_hosts` respectively; the Cordis host then discovers
declarative factories from `liteyukibot.cordis_plugins`.

Every enabled extension declares an ID and coexistence class. An extension ID
is exclusive by default and cannot be enabled in both hosts. The one exception
is when *both* declarations explicitly set `coexistence = "infrastructure"`;
that permits a first-party infrastructure extension to contribute to both
hosts. This is a topology guard, not a cross-host compatibility promise:
third-party dual-host coexistence remains best-effort.

Both hosts use the shared Extension API v2 declaration. Native extensions are
limited and require an explicit Permissions v2 capability ceiling. Cordis is
full by default and may only be downscoped through `[cordis.access]`. Cordis
provides scoped dependencies and deterministic cleanup alongside
ordered listeners, parallel fanout, waterfall middleware, directed predicate
routes, and a host-wrapped custom scheduler. It preserves the immutable
`EventEnvelope` as the only event identity. Neither host is a Python sandbox;
both retain bounded redacted operation audit records.

The public `PluginTestHarness` composes the same manager, event bus, service
registry, Action path, and managed tasks for single-plugin conformance tests.
It is not a second production host and does not depend on a test framework.
Broker peer conformance uses the real peer transport and installable example.

## Events And Actions

The implemented broker accepts a JSON-safe `EventIngress` from a registered
bridge. It assigns an immutable `kernel_event_id`, records the registered
bridge as source provenance, and selects subscribed bridge peers. A source
does not choose recipients or supply the kernel ID.

Broker delivery is FIFO per `(source_bridge_id, ordering_key, target_bridge_id)`
lane. `EventMessage` carries an opaque lease and `lease_ttl_ms`, not a
cross-process monotonic deadline. The broker alone evaluates timeout. A
delivery moves from offered through accepted and active to a terminal completed,
failed, or expired state; it is never retried. Events settle once all deliveries
are terminal, retaining successful and degraded diagnostics within bounded
active/terminal ledgers.

Actions are admitted only from an active delivery with its current lease. The
broker chooses an action owner from registered exact or prefix declarations:
the `full` access class wins before `limited`; exact resources are checked
before the longest matching prefix within the selected class. Same-class
ambiguity and registered ownership conflicts are rejected. Adapter-specific
behavior stays in the owning bridge rather than leaking into the broker.

The B7 kernel peer verifies source provenance, replaces the source envelope
ID with the broker-generated kernel ID, and publishes the result to the native
EventBus. Native plugin `SendMessage` actions may route back through the
delivered event's authenticated source bridge; the kernel declares no action
ownership. Generic API calls and message editing remain outside this portable
surface.

## Broker Peer Protocol

The B7 broker is standalone, not a child-supervisor IPC revision. LYIP v2 uses
separate directed ZMQ `control` and `business` lanes. A bridge authenticates
`bridge.register` on the control lane with its configured ID, instance token,
access class, subscriptions, and action-resource declarations. The broker
binds the peer identity, returns a session ID, and admits business frames only
on session-bound streams. Peers can unregister; a disconnect terminalizes
their outstanding deliveries.

Installed bridge entry points return the canonical
`liteyukibot.bridge_contracts.BridgeDefinition` containing `kind`, support
`grade`, owning `distribution`, and `launch` function. Broker re-exports this
type for import compatibility but does not own managed facet or artifact-store
implementations. NoneBot is the
stable framework reference; the adapter host owns separately packaged protocol
drivers. Framework SDK objects and credentials remain inside their owning
bridge packages; root composition does not import bridge SDKs.

The protocol-7 business catalog is `event.ingress`, `event.message`,
`event.accepted`, `event.completed`, `action.request`, and `action.result`.
Type ID, payload discriminator, lane, generation, stream sequence, and lease
are all validated. The ledger defaults to 1024 active events, 4096 terminal
events, 16 MiB of retained terminal wire content, 3600 seconds of terminal
retention, and a 30-second delivery timeout.
It provides bounded in-memory diagnostics only: no persistence, replay,
distributed delivery, or exactly-once claim.

The v1-v5 `RuntimeSupervisor`/`RuntimeClient` lifecycle and its
`liteyukibot.runtime` package have been removed. Bridge processes own their
framework lifecycle;
the stable NoneBot bridge and adapter host are configured in `broker.bridges`
and discovered from `liteyukibot.bridges`. Additional bridges need their own
adapter and lifecycle contracts. AstrBot, Neo-MoFox, and v6 compatibility are
retired source snapshots under `extras/legacy-bridges`, not v7.0.0 mainline
packages or supported bridge kinds.

## First-Party Bridge Hosts

The following packages are independently distributed bridge integrations. They
are selected through `broker.bridges` and keep framework-specific objects and
lifecycle state outside the kernel.

The former `liteyukibot-v7-runtime-nonebot` child host used NoneBot's official
initialization and adapter surfaces. The current package is a broker bridge:
it publishes normalized `message.created` events and owns only the portable
`message.send` action. NoneBot plugins, adapters, drivers, and Bot objects stay
inside the bridge process; `CallApi` and message editing are not portable B7
actions.

The `liteyukibot-v7-runtime-adapter` package is the independent Python host
for new protocol and platform adapter packages. It is a mixed-grade
`liteyukibot.bridges` entry point: configured driver instances publish through
the host's fixed topic map and own exact `message.send` resources. Adapters
publish a controlled `liteyukibot.adapters` entry point and own their SDK
objects, credentials, network connections, and event/action conversion inside
that bridge process. The kernel exchanges only frozen envelopes and never
imports an adapter SDK.

`liteyukibot-v7-adapter-onebot` hosts `onebot-v11` and `onebot-v12` entry
points with bounded HTTP Post, forward WebSocket, and reverse WebSocket
transports. It validates callback identity and token configuration, normalizes
private/group/channel structured message events, and executes portable actions.
`liteyukibot-v7-adapter-satori` is a separate external Satori v1 gateway
client, with native `IDENTIFY`, resume, and `message.create`; it does not embed
a gateway server or depend on Node. Both packages remain independent of
NoneBot and platform SDKs.

The `liteyukibot-v7-agent` package publishes two experimental limited Broker
bridges. `agent` owns provider state, bounded conversation history, progressive
Tool discovery, and one final source-bound `message.send` per event.
`agent-sandbox` is a separate no-subscription boundary for constrained worker
primitives. Neither bridge is a child Runtime or native plugin, and the
historical Runtime IPC Agent Tool/control path is removed.

## Versioned Contracts

The current public contracts live in the versioned
[specification index](../specs/README.md): Event and Action models, broker peer
IPC, LYIP, native plugins, configuration, management, resources, and v6
compatibility. Changes to these surfaces require explicit models, focused
tests, and the owning specification update rather than unannounced wire drift.

The implemented B7 broker protocol is version 7 and has no compatibility shim
for the child-supervisor v1-v5 catalog. The exact peer, delivery, registry, and
action rules are in the [Broker Peer IPC v7 specification](../specs/runtime-ipc-v7.md). Bridge integrations
must declare their manifest and lifecycle explicitly rather than relying on
legacy runtime settings.

## Operations

The `liteyuki` command (`ly` alias) validates configuration and plugin topology
and runs the local app. `liteyuki broker run` starts the standalone broker;
`liteyuki bridge run <bridge-id>` starts one configured bridge process. Named
instances derive private data, cache, logs, locks, and daemon state beneath
`.liteyuki/instances/<name>/`; the default retains its configured paths. Live
CLI operations authenticate through `data/control.json`. The optional HTTP
extra is read-only and rejects non-loopback binding at configuration
validation. Runtime-supervisor status, restart, heartbeat, and `/runtimes`
surfaces belonged to the historical child protocol and are not B7 bridge APIs.

`liteyuki broker inspect status`, `inspect events`, and `inspect event` expose
the bounded, redacted broker delivery ledger through a separate diagnostics
credential. The WebUI Event Deliveries view consumes the same read-only surface
and refreshes from its `event_delivery` SSE notification. Neither surface can
mutate broker state.

PyO3 is deliberately absent from the initial implementation. The architecture
first establishes measured Python baselines and stable boundaries. Rust is only
justified later for a profiled, isolated hotspot whose serialization and wheel
costs are lower than its measured gain.

`scripts/benchmark_v7.py` records startup time, event throughput, median/p95
dispatch latency, and peak RSS. CI uploads one baseline per operating system.
After the first stable release fixes reference values, a regression over 20%
requires an explicit performance review; noisy pre-release snapshots are not
used as an automatic pass/fail threshold. Schema 2 has two qualification
profiles: `bare` for the kernel with no extensions and `installed-first-party`
for the resolved first-party extension manifest. The parent resolves the
manifest once and passes the exact artifact to each independent sample child,
so profile artifacts are comparable only when both profile and manifest match.
The current three-run alpha reference and published-install matrix are
documented in
[`performance-v7.md`](../performance-v7.md).

## Current Release State

The current source pre-release is `liteyukibot-v7==7.0.0a14`. It is the Alpha14
lockstep bundle baseline, not yet a PyPI or stable release. The InstanceDaemon
currently retains ownership of the Broker -> Bridge -> Kernel graph and rolls
back a plugin generation whose bridge fails startup readiness. Alpha14 is
correcting the kernel, Broker, plugin-manager, daemon, and root-composition
ownership boundaries; the authoritative scope and exit criteria are in the
[`Alpha14 ownership and release baseline`](../roadmap/v7-alpha-14-baseline.md).

Current release procedure and package identities are in
[`development/releasing.md`](../development/releasing.md). Completed alpha
delivery phases are retained in the
[`documentation archive`](../archive/v7-alpha-delivery-history.md); the root
[`CHANGELOG`](../../CHANGELOG.md) is the release history.
