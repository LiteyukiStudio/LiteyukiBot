# LiteyukiBot v7 Architecture

## Boundaries

The core is a single-host microkernel. It owns configuration, logging, native
plugin lifecycle, services, event ordering, action routing, child supervision,
and local observability. Protocol adapters and compatibility frameworks are
child runtimes. Installed native plugins are trusted code; process separation
is a lifecycle and dependency boundary, not a hostile-code sandbox.

The kernel dependency budget is intentionally small: Pydantic and Yukilog.
YAML and HTTP are opt-in extras. Framework hosts and adapters are separately
published runtime packages discovered through `liteyukibot.runtimes` entry
points, so the kernel never depends on or imports a framework. uv exclusively
owns project resolution and locking; runtime package installation is not part
of the core.
The published kernel distribution is `liteyukibot-v7` and provides the
`liteyukibot` namespace. Compatibility namespaces belong to separately
published runtime packages, so the kernel has no framework or v6 dependency.

## Lifecycle

`LiteyukiApp` creates an immutable settings snapshot, event bus, service
registry, plugin manager, runtime supervisor, local control server, and optional
HTTP server. Startup validates plugin topology before launching child runtimes.
Failures trigger reverse cleanup. Shutdown rejects new runtime events, drains
accepted work, stops plugins and their tasks, then terminates child runtimes.

Native plugins are explicitly enabled and resolve from the
`liteyukibot.plugins` entry-point group or explicitly named local modules. An
entry point returns `PluginDefinition(manifest, setup)`. `setup(context)` is
async and may return start/stop callbacks. Service contracts use `name@major`
keys, one provider per key, and a startup dependency graph.

The kernel registers `liteyukibot.kernel.status@1` before plugin topology
resolution. Its provider exposes only frozen operational snapshots: version,
application state, monotonic uptime, plugin/runtime states, and EventBus
backlog. Native plugins do not receive a general `LiteyukiApp` handle.

The public `PluginTestHarness` composes the same manager, event bus, service
registry, Action path, and managed tasks for single-plugin conformance tests.
The public `RuntimeTestHarness` launches one real supervised subprocess for
protocol conformance. Neither helper is a second production host or depends on
a test framework. Installable examples and author guidance live under
`examples/` and `docs/development/`.

## Events And Actions

Runtime events become frozen Pydantic envelopes. The bounded bus preserves FIFO
order for `(runtime, bot, conversation)` and runs unrelated conversations
concurrently. Handlers return actions and an optional stop-propagation flag.
Failures and timeouts are isolated and reported; overload is an explicit result.

Actions are routed to the runtime named by their envelope. The initial portable
surface is `SendMessage` and `CallApi`. Adapter-specific behavior stays in the
runtime rather than leaking into the core.

## Runtime Protocol

Each runtime gets a random token and connects to a loopback TCP listener. Frames
use a four-byte big-endian length followed by UTF-8 JSON, capped at 8 MiB.
Protocol v1 covers hello/welcome, config, ready, heartbeat, child-originated
events, actions/results, shutdown, and errors. Protocol v2 is selected by an
exact hello/welcome version match and permits event/event-accepted pairs in
either direction. Core-to-child delivery additionally requires the
`runtime.events.receive` READY capability. Protocol v3 retains bidirectional
events and permits action/action-result pairs in either direction. A child may
submit Actions only after declaring `runtime.actions.send`; the core validates
them as protocol-neutral Action envelopes and routes them to the adapter runtime
that owns the bot. Protocol v4 carries an immutable `EventTrace` on
core-to-child deliveries. A v4 child that declares `runtime.events.complete`
also returns one terminal `event_completed` result after an accepted delivery;
the kernel records this as observability state and releases its delivery context.
V1 through v4 children may run together. Abnormal exits use bounded exponential
restart; clean exits do not restart.

All built-in child hosts use one async `RuntimeClient` for environment identity,
handshake validation, negotiated heartbeat, serialized writes, receive, and
idempotent connection cleanup. Its child-side Action correlation retains one
host-owned receive pump and fails pending requests on timeout, protocol failure,
or close. Framework hosts retain ownership of event and action dispatch; the
supervisor remains the sole restart-policy owner.

The `liteyukibot-v7-runtime-nonebot` package hosts NoneBot through its official initialization, driver, plugin-loading,
event-preprocessor, `Bot.send`, and `Bot.call_api` surfaces. Event forwarding is
observational and never suppresses NoneBot matcher dispatch. The child lazily
loads OneBot v11/v12 and Satori codecs, maps their conversation identity and
structured messages into frozen core envelopes, and reconstructs native
messages for replies and supported proactive routes. Adapter packages remain
optional and adapter objects never cross the runtime boundary.

The `liteyukibot-v7-runtime-adapter` package is the independent Python host
for new protocol and platform adapter packages. Adapters publish a controlled
`liteyukibot.adapters` entry point and own their SDK objects, credentials,
network connections, and event/action conversion inside that child process.
The kernel exchanges only frozen envelopes. Managed runtime generations permit
only their selected adapter entry points; the host ships without a platform SDK.
Before a managed generation becomes active, the kernel re-reads its immutable
manifest and load plan, then uses that generation's isolated Python to verify
the runtime distribution and `-m` host module can import. A failed probe removes
only the staged generation and leaves that runtime's active and rollback
pointers unchanged. This is an offline loadability gate, not an external
framework, credential, or network smoke test.

`liteyukibot-v7-adapter-onebot` is the first protocol package hosted there.
Its `onebot-v11` entry point owns a bounded HTTP Post event listener and a
OneBot HTTP API client. It validates callback identity and token configuration,
normalizes private/group structured message events, and executes protocol-
neutral `SendMessage` and restricted `CallApi` actions. It does not depend on
NoneBot, Node, or a platform SDK; OneBot v12 and Satori remain separate future
adapter packages.

The `liteyukibot-v7-runtime-v6` package owns the `liteyuki` compatibility
namespace and v6 child host. The kernel is the only runtime communication hub.
Configured event routes
deliver frozen Event envelopes from a source runtime to a distinct child;
child-originated Actions return through the kernel and route to the runtime
that owns the bot. Framework runtimes never connect to each other or exchange
adapter objects. The v6 compatibility namespace restores process-local session
models, rules, matcher registration, deterministic priority dispatch, and
ordered reply intents. Its historical message-only forwarding route remains
the default; it maps Events into the shared matcher registry and translates
ordered reply intents into protocol-neutral SendMessage Actions. It does not restore
Channel, shared-memory object transport, notices, requests, or adapter objects.

## Versioned Contracts

The current public contracts are recorded in the accepted
[architecture decision records](../adr/README.md): event/action schemas, local
runtime IPC, native plugins, configuration precedence, and error taxonomy.
Changes to these surfaces require explicit models, tests, and documentation
rather than unannounced wire drift.

ADR 0005 adds the negotiated protocol-v2 event direction, ADR 0007 adds the
protocol-v3 Action direction, and ADR 0022 adds protocol-v4 delivery tracing.
ADR 0008 defines their v6 message-plugin mapping,
ADR 0009 defines the NoneBot OneBot/Satori adapter boundary, and ADR 0010
defines the developer conformance helpers. ADR 0011 governs rapid pre-stable
iteration: v3 remains the direct-edit baseline, and a cross-cutting redesign
consumed v4; only v5 remains available before stable release. ADR 0012
defines the process-local kernel status service without changing runtime IPC.
No alpha protocol version may exceed v5. Existing v1/v2 support is tested but
is not a compatibility promise before the first stable v7 release.

## Operations

The `liteyuki` command (`ly` alias) validates configuration and plugin topology,
runs the app, lists configured or live state, and restarts runtimes. Live CLI
operations authenticate through `data/control.json`. The optional HTTP extra is
read-only and rejects non-loopback binding at configuration validation.
`liteyuki inspect topology` emits the resolved, redacted module graph: kernel
services, native plugin declarations, configured runtime health, and event-route
edges. Runtime options, child environment values, and secrets are never emitted.
The live status/control and optional `/runtimes` API expose runtime protocol,
capabilities, heartbeat age, restart-window failures, and bounded IPC counters
without exposing payloads or process credentials.

PyO3 is deliberately absent from the initial implementation. The architecture
first establishes measured Python baselines and stable boundaries. Rust is only
justified later for a profiled, isolated hotspot whose serialization and wheel
costs are lower than its measured gain.

`scripts/benchmark_v7.py` records startup time, event throughput, median/p95
dispatch latency, and peak RSS. CI uploads one baseline per operating system.
After the first stable release fixes reference values, a regression over 20%
requires an explicit performance review; noisy pre-release snapshots are not
used as an automatic pass/fail threshold. The current three-run alpha reference
and published-install matrix are documented in
[`performance-v7.md`](../performance-v7.md).

## Current Release State

The current source pre-release is `liteyukibot-v7==7.0.0a16`. The kernel,
bounded v6 compatibility, separately published runtime boundaries, and the
first-party plugin foundation are complete. Resources and profile remain
optional business plugins; their storage and migration ownership does not
belong to the kernel. The Beta1 compatibility tiers, supported installation
path, security boundary, and known limits are recorded in
[`beta1.md`](../beta1.md).

Current release procedure and package identities are in
[`development/releasing.md`](../development/releasing.md). Completed alpha
delivery phases are retained in the
