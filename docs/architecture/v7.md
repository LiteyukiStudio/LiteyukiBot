# LiteyukiBot v7 Architecture

## Purpose And Status

LiteyukiBot v7 is a single-host, protocol-neutral bot kernel that supervises
framework and adapter runtimes. This document separates the implemented
foundation from the planned Multiplane model. It is not a release plan and does
not assign work to a beta version.

The current implementation provides a Python kernel, native in-process plugins,
supervised child runtimes, LYIP ABI v2 over ZMQ, a bounded kernel event ledger,
local management, and a loopback WebUI. Cordis currently provides only a
closed first-party catcher manifest and PyO3 action planning package-core; its
Rust child transport and release-wheel binary packaging are not complete.

The versioned specifications in docs/specs remain the source of truth for
implemented public contracts. This page records the system boundary and the
accepted direction for the next implementation stage.

## Kernel Boundary

The kernel owns:

- configuration, secrets handoff, logging, runtime supervision, and local
  management;
- native plugin lifecycle and versioned service contracts;
- protocol-neutral Event and Action validation;
- event admission, per-conversation ordering, bounded dispatch, and action
  routing;
- the only supported communication path between runtimes; and
- redacted operational snapshots and local observability.

Framework SDK objects, adapters, bot objects, credentials, and framework plugin
state remain in the runtime that owns them. A child runtime is an integration
and lifecycle boundary, not a sandbox for hostile code. Native plugins are
trusted in-process code and do not receive a general LiteyukiApp handle.

The root package must not import a first-party runtime package. Runtime and
adapter distributions are discovered through entry points and define their
dependencies independently.

## Current Event And Runtime Model

An adapter or framework runtime produces a frozen EventEnvelope. The kernel
validates and admits it to the bounded EventBus. The bus preserves FIFO order
for each (runtime, bot, conversation) key while independent conversations run
concurrently. Native handlers may return protocol-neutral Actions. Configured
runtime routes can forward the same event to one or more child runtimes; an
Action always returns through the kernel to the runtime that owns its bot.

~~~text
source runtime
  -> kernel EventBus
  -> native handlers and configured child deliveries
  -> kernel ActionService
  -> source action-owner runtime
~~~

An ingress runtime sends `EventIngress(source_event_id, payload)`; it cannot
assign a kernel event ID or select downstream routes. The kernel admits it to
the bounded ledger, freezes the route plan, and issues one leased delivery per
selected target. `EventMessage` carries kernel and source IDs, delivery ID,
target, attempt, lease, deadline, and payload. Terminal outcomes are retained
as bounded, queryable kernel event state.

The active child transport is LYIP v1. It uses separate ZMQ business and
control lanes, authenticated launch identity, per-launch generation and lease
values, and per-stream sequence validation. The historical length-prefixed TCP
transport is retired and is not a fallback. See
[Runtime LYIP v1](../specs/runtime-lyip-v1.md) and
[Runtime IPC v6](../specs/runtime-ipc-v6.md).

## Runtime Classes

### Native Plugins

Native Liteyuki plugins run in the kernel and use the PluginManager, managed
tasks, versioned services, EventBus subscriptions, and ActionService. They are
the smallest extension surface and remain distinct from every child-runtime
plugin ecosystem.

### Classic Runtimes

Classic runtimes are framework compatibility hosts: NoneBot, AstrBot, Neo-MoFox,
v6 compatibility, and future comparable framework hosts. They retain their
native framework lifecycle, plugin APIs, adapters, and SDK objects inside their
own process. The kernel sees only frozen Event and Action envelopes plus
declared capabilities.

Classic runtimes are not a second kernel and may not connect directly to one
another. Their framework-local plugins are not Liteyuki native plugins and do
not gain cross-runtime object access.

### Cordis Plane

Cordis is an optional Liteyuki-owned Rust processor runtime under construction.
Its name refers only to scoped dependency access, reversible registration, and
deterministic cleanup inspired by Cordis concepts; it does not reuse Koishi or
Cordis JavaScript code, Session/Bot models, or event-chain semantics.

Cordis is not an alternative kernel and does not own adapters, credentials,
platform connections, global routing, or event identity. It is a processor
plane: it receives a frozen delivery, may execute its scoped catchers, and may
submit a protocol-neutral Action only while the kernel-issued delivery lease is
active. It communicates solely through the common supervised runtime protocol.

The implemented package-core owns a compiled, closed catcher manifest.
Configuration can select catcher IDs and override only non-empty exact
`match_text` and `reply_text` values. It validates dependencies, allows no
third-party manifests/services/markets/live reload, and produces at most eight
deterministic `SendMessage` plans per delivery through a narrow PyO3 JSON
surface. Its included `liteyuki-cordis` binary intentionally fails bootstrap:
it has no LYIP child loop and Maturin has not yet packaged the binary in a
release wheel. Cordis therefore must not be enabled as a runtime yet.

## Implemented Multiplane Model

Multiplane is a role model, not a claim that every runtime is interchangeable:

~~~text
Ingress runtime
  -> kernel event ledger and route-plan snapshot
  -> processor plane deliveries
  -> kernel action authorization and deduplication
  -> action-owner runtime
~~~

- An ingress runtime normalizes platform input but never selects downstream
  routes.
- The kernel assigns the Liteyuki event identity, retains source provenance,
  freezes the route plan, owns deadlines and delivery leases, and determines
  terminal state.
- A processor plane is a selected event consumer. Cordis is the planned Rust
  processor plane; a Classic runtime may also receive a delivery when the route
  explicitly permits it.
- An action-owner runtime executes the portable Action for the bot it owns.

Each route explicitly declares its target, `required` or `best_effort` policy,
and `sync` or `async` completion. Required failure affects the event terminal
state; best-effort failure is retained without doing so. Sync waits for required
delivery terminal state, while async returns after admission. Route changes
only affect subsequently admitted events because each event retains its own
route-plan snapshot.

## Event Ledger

The kernel owns a bounded in-memory event ledger with a state machine
equivalent to:

~~~text
admitted -> routed -> offered -> accepted -> active
                                      -> completed | failed | expired
~~~

For each admitted event, the kernel retains a bounded record of:

- a kernel-generated event ID and distinct source event ID/provenance;
- ordering stream and immutable route-plan snapshot;
- each delivery's target, attempt, lease, deadline, and terminal outcome;
- action deduplication keys and recorded execution result; and
- redacted diagnostic timing spans and failure attribution.

Disconnect, timeout, overload, and shutdown produce explicit state transitions.
The ledger has no retry, persistence, or replay; a restart may terminate
in-flight work. Active and terminal retention are bounded, so diagnostics cannot
create unbounded memory or storage.

The resulting public contract must state delivery semantics precisely. It must
not imply exactly-once delivery when an external platform action cannot prove
that guarantee.

## Diagnostics

The authenticated local WebUI service exposes read-only event-ledger pages at
`GET /api/v1/event-ledger?cursor=&limit=` and
`GET /api/v1/event-ledger/{event_id}`. SSE emits only an `event_ledger`
summary; details are fetched separately. The daemon projects worker records and
HMAC-redacts source runtime, source event, bot, and conversation identifiers.
It never projects payloads, segments, action payloads, credentials, or raw
exceptions. Diagnostics do not create a second event-state system.

## Non-Goals

- Remote administration, distributed runtime meshes, or durable cross-kernel
  replay.
- Direct runtime-to-runtime sockets or framework-object transfer.
- Treating process isolation as a security sandbox for untrusted plugins.
- A new Liteyuki Function DSL as part of the Multiplane foundation.
- Making the optional shared-memory primitive a lifecycle transport before an
  LYIP SHM adapter has the same proven semantics as ZMQ.
